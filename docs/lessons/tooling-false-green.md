# 工具与闸门的假绿

**什么时候会撞上**：闸门全绿但你心里没底。改了包结构、改了检查器、批量改了代码。报告「0 违规」。

工具报绿有相当一部分是真的什么都没检查。下面每一条都实际骗过人。

## 缓存与配置

`.importlinter` 改完或包结构动完，必须先删 `.grimp_cache` 与 `.import_linter_cache` 再跑契约。留着旧缓存，`lint-imports` 拿陈旧依赖图报绿，一整轮改动都白验。

契约名一律用英文。中文契约名配合 `PYTHONUTF8` 缺失会在 Windows 上乱码报错，省事的办法是别给它乱的机会。INI 文件必须无 BOM，PowerShell 5.1 的 `Set-Content` 默认写 BOM，configparser 会报「no section headers」，看着像配置文件坏了，其实是编码。forbidden 契约要禁第三方包，必须写 `include_external_packages`，否则它根本不看那批包。

`forbidden` 契约默认跟随**间接链**。想让「Qt 只出现在 `ui`」生效，源包填 `ui` 之外的所有层而不写 `allow_indirect_imports = True`，那么 `bot._main -> ui -> ui._windows -> PySide6` 这种完全正常的取窗链会被判 broken。想守的是「别直接 import」，就得显式放过间接。

## 检查器的参数与退出码

**校验脚本报「零违规」先怀疑它收没收对参数。** 有一类脚本的入参是 git ref 而不是文本本身，把整段文本传进去，它内部查不到、stdout 为空，于是客客气气报 0 条。任何校验工具第一次用，都要拿一个必然失败的输入验它会不会红——报绿不等于它跑了。

管道的退出码是最后一个命令的。`pyright | tail` 拿到 exit 0 是 `tail` 给的。判据要看到汇总行写着「0 errors」，或者取 `${PIPESTATUS[0]}`。

**「只报严重项」那类开关必须排在判定之后。** 同一个工具既做过滤又做统计时，过滤一放到前面，后面的统计就拿到残缺输入，会把一批仍在生效的登记项全算成失效，而且报得理直气壮、闸门照样绿。凡是带这类开关的检查器，先跑完全部判定再裁输出。验法：把开关打开与各关一遍，比对登记项的命中数与失效数，两个读数一致才算开关只动显示。

类型检查那类工具要用对入口：跑错文件会让内置类型全不解析，少带解释器参数会报上万条 `reportMissingImports` 的假错——**假错海会埋掉真错**，看着和「检查过了」一模一样。本项目用哪个 node、带哪些参数写在 [`../release-workflow.md`](../release-workflow.md) 的闸门命令里，命令会变，症状不会，所以只把症状记在这里。

## 覆盖面与探针

**0 命中不等于检查生效。** 新写的或改了判据前缀的规则，先造一个故意违规的探针文件确认它真能报，探针用完即删。改前缀之前还要拿新前缀对全量代码跑一遍，确认零新增违规，才敢断定覆盖面平移没缩水。

扫描器只查机械规则。docstring 检查查得出标点、括号、分号、折行、`-` 起头、空行，查不出「太长」和「黑话」。注释检查不判语义。这类质量必须导出全文人工审。跨私有性改动后 ruff 的 F821 能兜住悬空名，扫描器不查名字消费面——定义了公开名却在调用处写私有名，运行时才 NameError。

**能给违规登记静音的工具，要先按判据类型划线再决定让不让登记。** 判「关系对不对」的那类（谁引用谁、这个名字该不该对外）审过不改就真不用再看，登记一次省一劳。判「数到多少了」的那类（行数、个数、体积）一旦允许永久登记，等于对那个文件把度量关掉，越该动的越没声，而它恰恰是最容易攒出超限的地方。写静音机制时先把这条线划开，别按整节放行。文档里也要写明这类只认真改或认真抬阈值，不走登记。

门面漏导出只有 pyright 查得出，ruff 和单测都放过。反向探针的另一种打法：桩掉插件注册入口，喂一条假 Update 走框架的事件传播，可以在离线状态下验到路由与注入链路。断连与代理这类网络行为要用死端口实测取证，别只读代码。

**跨插件的拦截先后要靠真清单跑路由，桩出来的菜单查不出冲突。** 群里发 `/grant <id>` 一个字都不回，私聊只回「格式错误」：帮助插件把带任何位置参数都算多余输入，而授权命令恰恰要带 id。单测全绿是因为那份菜单是桩出来的假表、不含 grant，两条路由从没在同一张清单上碰过面。补完认参数的名单后，用真清单装配 Dispatcher、挂更新中间件、以假 session 挡住真发送，走 `feed_update` 才第一次验到「带 id 直接回执、不带 id 才提问、流程中别人发言不接管」。

**`create_task` 之后要有一轮调度，协程才真跑。** 验「常驻协程随轮询起停」时，假适配器的 `start()` 写成立刻返回的协程，测试就报「常驻协程 ran 0 次」——不是没启动，是那个任务还没被 loop 执行过就被 cancel 了。假 `start()` 里补一个 `await asyncio.sleep(0)` 让出一轮，才测得到真行为。同一个文件里还有一条：桩出来的假清单不含新命令，跨插件的路由冲突就查不出（见上一段那条真清单跑路由的打法）。

**对照组要先确认它真的会失败。** 有一次验「失效代理会不会拖死本可直连的请求」，对照组设的是代理软件常见端口，而那端口在你看不见的地方被重新监听了，对照组照样返回 200——结论看着被证实，其实是碰巧对上。换成 `127.0.0.1:9` 这种绝对无人监听的端口重跑，才拿到「裸请求 URLError、改后取到版本号」的干净证据。设对照组时顺带 `netstat` 看一眼那个端口在不在听。

**静态检查看不见运行期从磁盘加载的件。** 格式化、类型检查、依赖契约、规范扫描这四样只认仓库里的文件；外部插件与外部适配器是运行期挂上来的，静态层一律查不到，所以「外部件只准引接口包」这类规矩只能落在装载那一刻——导入之前扫它的源码。扫源码能覆盖函数体里的延迟导入（遍历的是整棵树），覆盖不了字符串拼出来的动态导入，写这道闸时要把这条边界写明，别让人以为它全能拦。

**反射式扫模块名字表找子类，会把 import 进来的基类本身也算进去。** 认入口类那一步要限定「定义在本模块的」（比类的所属模块名与当前模块名），否则每只老老实实 import 基类的插件都会被判成「不止一只入口类」。

## 改动落地与状态同步

**批量脚本的回执不能信。** 有一轮脚本报告改了 114 处，实际漏了一批：单行文本在 CRLF 与 LF 下计数相同，被当成「不需要改」跳过。同文件里按行号排序做多种改动会偏移，优先全文锚定。改完必须 grep 复核。

先落 import，再做使用它的编辑。新增符号的 import 如果晚于引用它的编辑，ruff 会把「导入了还没用」当死导入清掉，表现像改完自己回滚。删一个方法要连同它专用的顶部 import 一起删，否则同样被 ruff 判未使用。

临时脚本不要放项目根目录。根目录下有个 `libssl-3.dll` 之类的运行库，Windows 的 DLL 搜索顺序会让 python 先撞上它，表现为 `_ssl` 导入失败，和一个你正在跑的脚本毫无关系。

`docs/design/` 在 `.gitignore` 里，Grep 工具搜这个目录永远 0 命中，不等于没有引用。改路径时它要用命令行 `grep` 单独扫。

## 别信文档里的「已完成」

**「已实装」要用 grep 附文件行号坐实，零匹配就判未实装。** 设计文档与 CHANGELOG 的 Planned 段都可能写着「某层已完成」而代码里只有空包。抓过的实际形态：设计文档记着仓储已落地，实际那批目录只剩占位 docstring，契约声明的接口一个实现都没有。据此写发布文案或规划后续排期都会出错。

同一类坑是设计文档滞后于代码：文档列的字段与目录名和实际实现不一致，照文档施工会造出两套东西。动手前以代码为准，改完回写文档。

比较条件符号要逐条核对。权限判定写成「数值越小越特权」、比较用 `<=`，早期设计原文写的是 `>=`，照原文落码等于权限反转，且不报错、静默越权。这类反号只能靠实跑三档用户各发一条命令来验。

异常处理会吞掉取证。SSE 最后一个 chunk 的 `choices` 是空数组，代码取 `data["choices"][0]["delta"]` 抛 IndexError，被紧邻的 except 静默吞掉，表现是 usage 永远统计不到，日志里一条错都没有。取前先判空。

## 闸门红不一定等于代码坏

pyright 突然报某插件目录下几行 `reportMissingImports`，先看那个插件的依赖还在不在开发环境的 `.venv` 里，别去改代码。**「同步依赖」按启用清单重建依赖闭包，禁用插件的依赖会被真卸掉**（开发模式下装库器找得到 venv 里的 uv，走的是真装卸，装卸日志记着实际卸载了哪些包）。判据是实例的启用清单成了空集，而报错只落在声明这些依赖的那个插件包内。重新启用插件会走补装，或按需要单独装回那几项。

## 外部审阅给的结论也是待验输入

外部会话（人或模型）交的清单带着 file:line，看着像施工图，实际只是待验输入。它有两块天生的视野盲区，本机工具能看见、它看不见。

- **它不知道质检线的阈值与豁免表。** 它判「这段规则写错了地方，该搬去某文件」，方向是对的，但那个目标文件只剩下不到一行的余量，搬进去当场顶破单文件行数触发线，把待核基线往上抬一格，而基线只许减不许增，于是整条建议落不了地。同一条建议在下一轮被原样重复一次，因为它看不见上一轮为什么撤回。**落之前现量两样：目标文件的余量，以及落点文件到底存在不存在。**
- **它写落点时，新建文件与既存文件用同一种句式。** 一句「放在某文件的某个函数里」配着链接，读起来像那儿已经有那个文件，其实两个都要从零建。涉及新建结构的建议，先跑一次存在性检查，再按「新结构要逐件对现成先例」的规矩问一句。

引条文号错位不等于结论作废。它把一条禁句条文引成了另一条禁句条文，条文引错了，删那一句的判断仍然成立——纠文不纠案。
条文改对，结论按自己的判据再复核一遍。反过来也别因为引错就整条作废，那样会把真问题一起扔掉。

喂给它的表如果被截断过，它多半自己会声明「未展开的位置不评价」。这句声明出现在产出里，就说明输入不完整，要么补全量再跑，要么只按已展开的部分下结论，不许让它替未读过的部分背书。
