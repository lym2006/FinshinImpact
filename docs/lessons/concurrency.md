# 跨线程与并发

**什么时候会撞上**：写 asyncio 协程、动 bot 的长轮询与重连、界面与引擎之间传消息、加定时器。

## 事件循环里不许有同步阻塞

协程里做同步磁盘读写，磁盘一慢就冻住**整个事件循环**：所有流式输出、长轮询和 GUI 一起停摆，症状像程序挂了而不是某个任务慢。落盘一律 `asyncio.to_thread`。

同理，等待信号时别在协程里同步 `wait()`。退避等待要写成 `asyncio.to_thread(stop_event.wait, ...)`，直接 `sleep` 会拖满一个周期，直接同步 `wait` 冻循环。

## Qt 与引擎之间只走一座桥

`ui/_bridge` 的信号桥是 bot 与界面唯一的通信面，**全项目只能有一个实例**。搬迁它时不要留旧路径的转发 shim：留了 shim，漏改的一方静默走旧路径，两套信号实例并存，跨线程关闭屏障失效，表现是偶发不响应而不是报错。删掉旧路径让漏改直接 ImportError，是最省事的防线。

验单例的办法很直接：把各消费模块里的对象和门面取出的对象比 `id`，全等才算一个实例。再看 `sys.modules` 里旧模块名不存在。防重连这类语义要靠实跑（同 tag 连两次只触发一次、断开后能重连、关闭屏障正常），看代码看不出来。

不是所有 GUI 联动都该上信号。断连计时弹窗最后改走「状态单例加定时器轮询」，原因是按 tag 防重连的信号桥给心跳链路添负担，而探测模块不碰引擎、能保住界面到工具层的单向依赖。判断标准是这条通知要不要立刻送达，周期性状态展示用轮询更便宜。

定时器全部经 `ui/_lifecycle` 的 `Ticker` 抽象，上层禁直接 import `QTimer`。它保证 start 幂等（在跑就不重置节拍）、`after` 是即发即忘的一次性延时、`repeats=False` 时可停超时。全项目 `QTimer` 只剩泵内一处是刻意维持的口径。

## 重连与超时语义

长轮询的重连不要靠外层装饰器。引擎的接收循环内层自己有无界重试并吞异常，断网时异常到不了外层，外层重试实际只在启动那一下的窄窗口里生效。摘掉外层后那个窄窗口反而成了真空，重试逻辑要收回协程内按固定退避重跑。别同时保留两套重连叙事。

读超时和整体超时的语义不同：流式场景「超时」是等下一块，非流式是等整个响应。把流式请求按非流式超时配，长回答会被误杀。砍功能时别顺手把传输层的流式也砍掉——展示层的打字机效果可以没有，传输层的分块要留着。

判「链路断了」要用异常族白名单，不要接在最顶层异常下。某类网络错误挂在通用 API 错误之下，代理层还会裸穿几个专用异常类，漏判一类就全程静默不报。异常原样往上抛，别让一个「代理被拒」显示成「服务器异常」。

断网到弹窗之间有个静默窗口（两次三十秒超时叠加的量级），别看到它沉默就以为检测没工作。请求超时定在 30 秒（`utils/network/_session.py:35`）而不是框架默认的 60 秒，连续两次失败才起计时、弹窗、打日志（`utils/network/_link.py:16`），单条抖动零输出——这三样是同一个判据的三个面，改一个要想另外两个。

断连与恢复的痕迹已经由探测模块自己打到专用日志器上，仪表盘挂的是根日志器，所以面板天然看得到。**别在别处再补一句打印**，补了就是同一件事两行。

「断网约 60 秒才跳窗」不是计时器设的，是挂死型请求撑到会话总超时才抛异常——看代码找那个计时器会找不到。
