# 迁移与改名

**什么时候会撞上**：搬目录、改符号名、把散在几处的实现收拢成单源，或者要给老用户的数据做兼容。

## 改名与搬迁的操作纪律

改一个键或符号的调用点之前，grep 全量消费方。行号只是当时快照，曾经因为 import 漏网让改动只生效一半。`docs/design/` 被 gitignore，Grep 工具搜不到它，要用命令行 `grep` 单独扫。

搬包结构时**不留旧路径的转发 shim**。漏改的一方会静默走旧路，两套实现并存，症状推迟到运行时才暴露。让漏改直接 ImportError 更省命。过渡期非要留 shim 的话，只做惰性转发并保证它是**同一对象**（`a is b` 断言坐实单源，别弄成副本）。

git 的重命名识别只在相似度够高时生效，搬家时纯移动代码、别顺手改内容，否则历史里那一笔看不出是搬家（实测落在 90~98% 区间能识别）。删一个包不能只 `git rm` 已跟踪文件，剩下的 `__pycache__` 会让目录看着还在，要连目录一并清。删前 grep 全仓（含 tests、packaging、pyproject）确认真零引用。

批量改文本的脚本坑在换行符：单行文本在 CRLF 与 LF 下计数相同，会被当成「不需要改」跳过（实际漏过 114 条）。单行按 `count(old) == 1` 直接替换，多行才准备 CRLF 变体。同一文件里按行号排序做多种改动会偏移，优先全文锚定。改完必须 grep 复核，别信脚本回执。

## 数据与格式迁移

老数据导入后把源文件改名留档（加 `.migrated` 尾缀）而不是删除，给自己留一版回滚窗。

**两个会产生新存储结构的阶段合并成一版发**，别让用户连续遭遇两次不可回滚的降级。库文件里的 schema 版本高于代码认识的版本时直接拒启并弹窗指备份位置——回滚后读未知结构比拒启严重得多。

键的形态要受文件系统约束：Windows 文件名不许有冒号，凡是把外部键直接当文件名的落盘都要先过一个名字净化函数。清理循环若按净化前的键找文件，会留下一堆无人认领的临时目录且不报错。

迁移的考古办法：上游项目缺文件时，残留的 `__pycache__` 能反推曾经存在过哪些模块。

## 什么时候不该动

用户已经看顺眼的界面观感是契约。已经定稿的命名口径（例如「引导期」「面板」「实例」这些词）改动要连带文案指针一起改，别只改代码。纯注释与措辞整改不属实现方式变化，不进 CHANGELOG。

散文里写死标识符、模块路径或行号，改名后没人通知它，于是悄悄失效还看着像真话。要交代影响范围就写角色类别，比如「建钮处」「各窗样式选择器」。有意做单源指针的例外是注释里的 `# 用：<路径>`，那类必须随搬家同步更新，改错一处就成死链。

同一道理，设计过程文档属易腐内容。做完的批次留「哪笔提交、验到什么」的实录，通用经验移进本档并跟着代码现状维护，别让一份不进版本库的草稿成为唯一留档。
