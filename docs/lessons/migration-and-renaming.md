# 迁移与改名

**什么时候会撞上**：搬目录、改符号名、把散在几处的实现收拢成单源，或者要给老用户的数据做兼容。

## 改名与搬迁的操作纪律

- 被忽略目录的搜索盲区见 [改动落地与状态同步](tooling-false-green.md#改动落地与状态同步)。

搬包结构时**不留旧路径的转发 shim**。漏改的一方会静默走旧路，两套实现并存，症状推迟到运行时才暴露。让漏改直接 ImportError 更省命。过渡期非要留 shim 的话，只做惰性转发并保证它是**同一对象**（`a is b` 断言坐实单源，别弄成副本）。

git 的重命名识别只在相似度够高时生效，搬家时纯移动代码、别顺手改内容，否则历史里那一笔看不出是搬家（实测落在 90~98% 区间能识别）。删一个包不能只 `git rm` 已跟踪文件，剩下的 `__pycache__` 会让目录看着还在，要连目录一并清。删前 grep 全仓（含 tests、packaging、pyproject）确认真零引用。

批量改文本的脚本坑在换行符：单行文本在 CRLF 与 LF 下计数相同，会被当成「不需要改」跳过。单行按 `count(old) == 1` 直接替换，多行才准备 CRLF 变体。同一文件里按行号排序做多种改动会偏移，优先全文锚定。改完必须 grep 复核，别信脚本回执。

写进文件的路径要按字面留反斜杠：改动串在被写入前被解一次转义，`\b` 与 `\t` 就落成退格和制表符，`dir\backup` 变成 `dirbackup`，肉眼看不出坏了。改完扫一遍控制字符，比盯渲染结果可靠。

**用 `git submodule` 登记时，搬目录名 git 不会把三处一起搬走。**

- `git mv` 只挪工作树与索引里那条 gitlink，`.gitmodules` 里的段名、`.git/config` 里的 `submodule.<名字>.*`、`.git/modules/<旧名>` 三处都不跟着改。
- 只改 path 那一行的话，`git submodule status` 会给出前导 `-`，看着像没检出，要 `git config --rename-section` 补上再 `git submodule sync`。
- 内部那个 modules 目录名 `absorbgitdirs` 也不会搬，留着旧名不影响使用，别为了好看去手改 gitfile 里的路径。
- 改完三条自检：子仓 `git status` 干净、主仓 `git status` 不报指针变化、`git ls-files -s <登记路径>` 的 sha 与子仓 HEAD 相同。

**改一大片要拿等价性证据，别只说「行为没变」。** 把新旧两套取法各跑一遍，逐类或逐项对比结果，报出「N 项一致、0 项不同」这种数。只跑测试不够——测试可能压根没覆盖被改的那一项。对比表是当场能抓住「顺手改了语义」的唯一便宜办法。同一趟里还要报改动面（几份文件、几行），两个数一起才说明白这次动得多深。

## 数据与格式迁移

老数据导入后把源文件改名留档（加 `.migrated` 尾缀）而不是删除，给自己留一版回滚窗。

会产生中间态的变更合一次发，判据见 [发版节奏上的两个坑](deps-and-release.md#发版节奏上的两个坑)。库版本号高于代码认识的怎么处理见 [schema 版本只许向下兼容，且要挡住向前](config-and-data.md#schema-版本只许向下兼容且要挡住向前)。

键的形态受文件系统约束的成因与后果见 [Windows 文件名不是通用键的载体](config-and-data.md#windows-文件名不是通用键的载体)。

迁移的考古办法：上游项目缺文件时，残留的 `__pycache__` 能反推曾经存在过哪些模块。

## 库结构迁移的编号、内容与时机

结构变更靠一组按编号排序的脚本落进用户的库：版本表里一行记一个已应用的号，启动时按顺序补做没跑过的，一支落定才提交，然后才轮到下一支——备份要放在上一支提交之后，否则副本里混着半支改到一半的结构。

**号只用追加，改结构开新号**。

- 每支脚本的源码哈希随版本号一起记账，脚本内容改了老账就对不上。
- 更要紧的是已经补做过这一号的库不会再跑第二遍，往旧脚本里新加的动作那些机器永远学不会。
- 反过来，把新形状直接写进基线、指望它替掉已发出去的增量，也不行：基线一旦被增量脚本改过，重放基线会在增量删掉的列上重建索引而失败，「清空版本表从头建一遍」这条本地自证的路当场断掉。
- **发布前做一次大型破坏性收敛是允许的**，代价就是接受基线不可重放，并且只在这份收敛之后没有任何增量出门时才划算。

**该不该走迁移，看停写以后老库当场报不报错**。撤掉一个 `NOT NULL` 又没默认值的列，写入侧不再填它，每条新记录当场违约——这种只能靠迁移抹掉，光改代码会让后续步骤静默死掉。只撤读、列留着无害的，可以等真正要收敛结构时一起抹。一次把加了又删的东西变干净，写一支只删不建的脚本即可。

**脚本要敢重跑**。逐列先查在不在，在才删。建在被删列上的索引必须先撤，`ALTER TABLE ... DROP COLUMN` 在列上挂着索引时直接失败。整套动作用 `IF EXISTS` 与「先核再动」写成幂等，重复执行不报错。删列本身要求 sqlite 3.35 以上，嵌入式解释器带的版本要一并确认。

**会回一行的语句不取空就锁着库**。查列名、查版本、让 WAL 落盘这几条都会返回行。

- 用通用执行接口发出去却不取空，游标悬着，库结构被它锁住，随后的撤索引与删列当场报 "database table is locked"。
- 建表类语句不回行，所以只有基线的时期看不出这个问题，第一次做删列才暴露。
- 凡回行的语句一律走「取完即关」的写法，改完当场拿一条删列语句验一次——报 locked 就是这个原因，别顺手怀疑删列语法。

**备份的判据用版本表有没有行**。迁移前把 WAL 里已提交的内容落回主文件再复制，否则副本缺最后一段。全新库一落盘就是 4096 字节而不是 0（WAL 写头部即刻落文件），所以「文件为空即新库」这个判据永远不成立，每台新机器会白留一份几乎空的备份。版本表一行都没有才说明结构正在从零建立，那时没什么可丢。

## 什么时候不该动

已经定稿的命名口径（例如「引导期」「面板」「实例」这些词）改动要连带文案指针一起改，别只改代码。纯注释与措辞整改不属实现方式变化，不进 CHANGELOG。

散文里写死标识符或模块路径，改名后没人通知它，于是悄悄失效还看着像真话。影响范围与 `# 用：<路径>` 单源指针的写法见 [指针写法](../writing-style.md#指针写法)。

同一道理，设计过程文档属易腐内容。做完的改动留「哪笔提交、验到什么」的实录，通用经验移进本档并跟着代码现状维护，别让一份不进版本库的草稿成为唯一留档。
