# 依赖、进程与发布

**什么时候会撞上**：加第三方包、装库、起子进程、改打包链路、发版前最后一道检查。

## 打包产物拷源码，不做静态分析

发布走打包脚本（用法在 [`../packaging.md`](../packaging.md)），把源码与资源整目录拷进包里，配一份内嵌 Python 运行。PyInstaller 只用来打安装壳那一个可执行文件，不分析项目代码。

这条事实推翻一大类担心：

- 惰性门面的 `importlib.import_module(变量名)` 不会被漏收，因为模块文件本来就在包里。别去查 `hiddenimports`，也没有 hook 要写。
- 冷启动慢不是 PyInstaller 的解包开销，是真的在 import。想量就用 `python -X importtime`，别猜。
- 反过来，包里的源码是明文可改的。别把任何凭据写进代码指望「打包了看不到」。

## 加依赖前先问首启能不能离线

装库链路要在用户机器上无网、无编译器、无管理员权限的环境下跑通，这砍掉了两类常见选择：

- 需要联网下载模型或词表文件的包（官方的 tokenizer 就是这个毛病）——首启离线安装直接失败。
- 分词准确性依赖特定词表、且只对某家 API 准的包（`tiktoken` 之类）——本项目接的是多家兼容端点，算出来的 token 数不对，反而让人以为预算控制生效了。判断上下文压力用平台返回的 `usage`，不要自己数。

需要新依赖时，先确认它在「内嵌 Python + 离线 + 纯 wheel」下能装上，再谈功能。

## 起子进程只有隐藏窗口这一条路

Windows 下用 `subprocess` 会闪一个黑框，用户以为程序崩了。项目里有一个统一起子进程的入口，把 `CREATE_NO_WINDOW` 与标准句柄处理收在一处，起进程只准走它。自己新起子进程而不经过它，就等于给发布版加了一次闪窗。

装库这类长任务必须有可见进度，并且能取消。用户等在半秒没反应的窗口前，唯一确定的是「这程序是不是挂了」。

## 环境代理是全局告示牌，会毒死本可直连的请求

启动器把注册表系统代理写进 `HTTP_PROXY` 与 `HTTPS_PROXY`。本意是给安装期的 pip、uv、playwright 子进程用，但环境变量立在进程里，**启动器自己出门也读它**。`urllib` 默认从环境发现代理，于是一个失效的代理地址会让版本页与加速镜像一起失败——而这两条本来都不需要代理。

实测过的可达性（2026-10，代理内核完全未启动、无任何代理）：GitHub Pages 与 `api.github.com` 直连 200，`raw.githubusercontent.com` 不通。所以「版本页得开代理才能读」是错觉，代理恰恰是它读不到的原因。真正需要代理的只有 Telegram 收发，那条走应用内的三级解析，与启动器无关。

做法：启动器自身取数一律经一个统一取数入口拿通道，一条显式屏蔽环境代理与注册表发现，一条才走代理。顺序是先干净直连把全源试完，失败再带代理补一轮。装库子进程照旧吃注入的环境变量，行为不变。

推论适用于一切子进程场景：别为了传配置往自己进程环境里写全局变量，要传就显式传 `env=`。告示牌影响的从来不只是你想让它影响的那几个。

## 装库：判「装没装」要查盘，不要信指纹

启停插件**永远不该引发装卸**。判「装没装」只准实测：pip 逐包问询加资源磁盘探活。计划为空就静默放行，绝不因为「配置变了」弹窗。真缺项才起进度窗补装。

摘要与指纹那类东西只适合做「目录变了没」的侦测，一旦拿它判存在性，就会出现「记录说装了、盘上没有」的实际不可导入状态。资源探活分两级，先便宜的：磁盘 glob 匹配 `{slug}-*`（毫秒级，够启动判定用）→ 落空才走 dry-run 的权威目录复核（约 0.9 秒子进程，只兜底）。

删除判据必须**跨实例无主**。运行时依赖层是全局共享的，实例目录里的清单只存启用状态。只看本实例就把包卸掉，会砸了另一个仍启用它的实例。所以求的是「排除本实例后所有实例的并集」的差集。

## uv 与 sync 的三个致命细节

- **`sync` 不许直喂顶层依赖名**。实测会把全部传递依赖删掉（提示 Would uninstall 44）。必须先把依赖 compile 成完整闭包，再 sync 那个闭包。顺带两个坑：`sync` 认位置参数不认 `-r`。`-e 项目根` 这种裸路径别加引号，compile 会把引号当路径字面量。
- **验这条路必须 mock 掉真正执行 uv 的那层**。曾经真跑过一次，把开发环境的 venv 削残，pytest、rich、grimp、PySide6 的 DLL 全没了。
- **清缓存要 `uv cache clean --cache-dir` 才全清**。`uv cache prune` 实测无效：成套缓存被判「全部在用」，报 No unused entries，而且它不吃 `--python` 参数、拼进标志串会直接 exit 2。

浏览器内核这类共享资源，卸载命令只解除引用不物理删。加 `--all` 会误伤机器上其它程序，故意不加。

`uv` 自身按三级查找：包内运行目录 → venv（多个候选目录名乘多个可执行名）→ PATH。找不到就降级成把手工命令原样印给用户，命令里带上 `uv pip …` / `python -m …` 让用户能直接贴。装库常量（镜像地址、缓存目录、CDN）单源在 `pyproject.toml` 的工具段里，启动器与装库器共读、**不留兜底默认值**——缺键就大声失败，因为静默回退会得到第二个不同的镜像源，那种不一致比崩更难查。

装依赖时带 uv 原生的字节码预编译开关，首启就不用现编。卸载不需要（孤儿 `.pyc` 实测 `find_spec` 返回 None，不可导入，留着无害但别当成没删干净）。

## 凭据进过代码就等于泄露

迁移期代码里硬编码过 API key 与站点 Cookie，Cookie 的过期时间戳换算下来早就失效。这两件事的结论一样：**进过版本库的凭据一律按已泄露处理，必须轮换**，不能因为「文件已删」「它已经过期」就认为安全——文件在历史里，克隆过的人随时取得。

同理，发布包里 `profile.json` 存 token 的目录属用户资产，升级要保留，但绝不能进任何日志、报错文本或反馈附件。

## 发版节奏上的两个坑

数据库 schema 迁移和依赖清单变更不要分两次发。分开发就要为中间态写兼容代码，而中间态在用户机器上的停留时间不可控。合到一次发版，兼容窗口只存在一个版本号内，能验完。

改过启动器源码必须重跑打包脚本。产物指纹跟着源码走，忘了重跑就出现「仓库里是新的、包里还是旧的」，症状是客户端行为与 CHANGELOG 对不上，很难往回查。现网复发过一次：代理修复比那个号的包晚一小时构建，传上去的包里不含该修复，只能留给下一个号。**判据是比对产物构建时间与改动文件时间，别看版本号像不像**。

打包脚本自检模式的末行打印在线版本页号，翻页了才算闭环——发布动作和升级链生效是两件事，中间隔一个 Pages 部署延迟。
