# 大模型调用、成本与人设

**什么时候会撞上**：换模型、调上下文预算、写人设、动压缩策略、做权限相关的对话行为。

## 成本结构决定了两个动作的优先级

按 2026-10 的千问报价实测（月 15000 次请求、每次输出 100 token、缓存命中按现实 70% 算）：

- **输出比输入贵得多**。输出单价是缓存命中输入价的 20 倍，全命中时一轮 100 token 的输出成本高于 9000 token 的输入，占账单约 69%。所以**控制回复长度是最高杠杆的手段**，人设里的长度规范（日常 20~80 字）不是可选项——回复从 100 token 涨到 200，月成本从 ¥13 变 ¥21。
- **缓存命中率是第二杠杆**。命中率从 100% 掉到 0%，月成本从 ¥8.7 涨到 ¥25，约 3 倍。前缀里任何一点抖动都会付这笔钱。

这两条是「人设写短」「压缩别太频繁」这类要求的真实理由，不是审美偏好。

## 阈值不是拍的，是价格阶梯逼出来的

压缩触发定在 16384 token，因为千问的计费在 32k 处有悬崖：超出后输入单价从 0.2 涨到 0.6、输出从 0.8 涨到 2.4，都是 3 倍。16k 留两倍余量待在最低档。同一份测算给出的敏感性：8k 阈值月成本 ¥7.5、只能记约 46 轮原文。16k 是 ¥13、约 97 轮。32k 就 ¥24 了。多花的 ¥5.5 买的是翻倍记忆深度。

注意两组数字量纲互不可比：压缩阈值算的是整包上下文（人设 950 + 每轮约 150，所以对应 90~100 轮），窗口 32k 算的是模型上限。把它们混为一谈会得出自相矛盾的结论。

永不触发的阈值是负资产。压缩之后上下文只剩几千 token，按满窗设的那些阈值压根到不了数，留着一个永不触发的阈值会让后来人以为它在保护什么。加这类参数前先算它在当前预算下够不够得着。

## 缓存只吃隐式的，且人设必须逐字节稳定在最前

隐式缓存默认自动开启、无法关闭，命中部分按输入价 20% 计费，最小触发 1024 token。三条推论：

- 人设放 messages 最前，且内容**逐字节稳定**。在人设里拼时间戳、日期或随机语，等于每次请求都换前缀，缓存全失效、成本涨约 4 倍。历史按原顺序追加、不回改不重排，改名不回写历史这条惯例正好配合。
- 人设压缩后约 950 token，**单独不够触发** 1024，要靠「人设 + 部分历史」合并命中。所以人设不宜再精简到远低于这个数。
- 显式缓存不用。TTL 只有 5 分钟，群聊间隔常超过，而创建要按 125% 付费——命中率低时反而纯亏。

压缩本身每次都断一次前缀，之后重新累积命中，这是「压缩不宜过频」的成本理由，不只是体验理由。

## 模型选型的两条容易被复述错的结论

- 弃 SiliconFlow 不是因为不好用，是同模型贵 1.5~3 倍、缓存命中价贵 5 倍。切换只改 `base_url` 与 `model_name`，代码不动。
- 免费的小模型只适合零成本试提示词，不代表能担当线上。拿它的表现推断付费模型是错的，反过来也一样。
- 平台页面上同一模型的「上下文长度」可能有三处互相矛盾的数值（本项目实测到 32768 / 262144 / 8k 三个说法）。这种分歧只要不影响淘汰判据就不必纠缠：8k 装不下 16k 阈值直接出局，32k 勉强够、零余量。别为了确认一个官方没写清的数停下整条选型。

## 默认人设换版的传导规矩

内置默认模板与实例里的 `persona.md` 靠内容指纹比对，参与比对的有三方：副本内容、模板内容、`.persona.base` 里记的「最近一次与该实例打交道的模板指纹」。

- **行尾转换不算改动**。指纹按读成文本再编码算，编辑器把 LF 换成 CRLF 不会被误判成用户改过。
- **只有拿得准「从没改过」才自动覆盖**。副本等于模板即静默补戳。副本等于戳所记的旧模板即自动换新、只记日志。判不出的一律弹窗问，绝不用模板盖用户内容。
- **副本读不出即不动**。指纹无从比对时覆盖会毁掉读不到的内容，直接跳过这条。
- **动盘的只有启动那一次**。启动对账受「本版已提示过」抑制，同一版模板只打扰一次。预览窗把渲染后的正文摆在窗底，草稿没落盘才多一行提示，读的全是内存，点不点覆盖都改不了盘。运行期不读实例文件，外面手改的一律不跟读，要它生效只能点面板上的"从文件重新加载"：读到的一样就报一句无变化，不一致才弹窗选哪份，关窗不算选、要重载再点一次。
- **提示窗没关过不算已提示**。落戳发生在关窗之后，中途崩了下次启动接着提示。
- **「保留我的人设」只结清当前这一版**。它落的是本次模板指纹，下一版模板出来照旧再问一次。改过的副本无法事后证明没改过，所以每版都要用户当场定夺，这是设计不是缺漏。
- **副本还没建时由写入侧补建**。落正文与一键覆盖都先按默认模板建好副本再写，建不出才提示目录不可写。
- **改随包默认件即换全局默认，认了**。`assets/persona.example.md` 整目录进发布包，别人机器上的模板只在他自愿升级时换新。手改这份文件只影响自己机器上那些从没动过人设文件的实例，静默换新还要求副本等于戳登记过的模板指纹，拿不出这份证据的一律弹窗。
- **人设只有一份文本，走文件**。配置里不再有人格字符串，正文取磁盘副本。
- 副本读不出退随包 `assets/persona.example.md`，模板也读不出退空正文并记错误。留第二条正文口子等于两处维护同一份人格，早晚对不上。
- **多余键不炸读、保存即清**。实例 `config.toml` 里已存的旧字段按字段表读取时被忽略，面板保存走整份重写，点一次保存即把废弃行清掉，不需要迁移代码。

坑：正文缓存在程序里分生效、备份与草稿三格，预览和编辑读的都是草稿那格。草稿顶成生效只发生在保存配置起校验轮那一刻，校验没过或用户中止即退回顶替前那份备份，正文写进盘才按新文件重装生效格并把草稿一起清掉。让预览或编辑当场顶生效格，就等于替用户改了运行中的正文，还会把「文件被外面改过」这个信号提前吃掉，之后再也报不出来。

坑：把读盘收进缓存之后，**装填必须排在配置应用之前**。对话身份的基准是在配置应用那一步取的，正文还没装填即基准落成空串，用户下一次点保存会被判成「人设变了」，连会话历史带 `records/` 一起清掉——什么也没改却洗了历史。原来那个「首次用时顺手读一次」的懒加载恰好挡住了这个坑，撤掉它就得把装填时机显式提到前面，别指望调用方自己去读。

## 防冒充的真防线在代码，人设只是话术

OWASP 的提示词注入防御建议里明写：**不要仅依赖提示词**。面对越狱类手法（DAN、假设情景、角色扮演套娃），纯 system prompt 声明会失效。所以人设的定位是「降低概率 + 保持体验」，权限判定一律走代码：主人名单在配置里，命令角色由领域层的角色表判定，中间件校验。

其中最关键的一环是**每条消息由系统注入 `sender_id`**：AI 拿到的是客观 id，而不是用户自称。这让「有人自称主人」在数据层面站不住脚，比任何措辞都可靠。

实测证据（2026-10-06，qwen3.7-flash）：

- 只靠人设挡不住改名——收到 `/set name 咪咪` 就接受，次轮自称「我现在叫咪咪」。
- 会编造不存在的功能——同一次实测里 AI 凭空造出 `/set avatar`、`/reset`。自然语言问功能时代码拦不住，全靠人设话术推挡 + 让对方自己 `/help`。

## 写人设的四个有效做法

- **用肯定句不用否定句**。「你就是纳西妲」优于「不要说自己是 AI」——否定句反而把 AI 这个词引入了上下文。
- **硬规则放最前**。模型对 prompt 开头的注意力权重最高，身份约束用开头 + 结尾的三明治结构。
- **台词样例宁少勿多**。从 40 多条砍到 7 条：样例过多会稀释指令权重，社区观察到角色定义占到上下文一半时指令遵循度明显下降。
- 人设正文走文件读取加变量注入（代码读 `persona.md`、自动填主人 id），不要在配置里手工替换占位符——两处维护同一个 id 迟早对不上。占位符字符串单源成常量，模板写侧与注入读侧必须同值。
